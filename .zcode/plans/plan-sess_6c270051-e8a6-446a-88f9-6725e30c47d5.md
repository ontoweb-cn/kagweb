| 项 | 采用 | 理由 |

## 第二部分：批次三 — profile 的 `model` 与 `context_window`

### 2.1 后端：profile 归一化
`kagweb/services/config/runtime_settings.py`：
- 新增边界常量 `AGENT_LOOP_CONTEXT_WINDOW_RANGE = (1_024, 1_000_000)`（上限对齐已有的 `MAX_EFFECTIVE_CONTEXT_WINDOW`）。
- `_normalize_agent_loop_profile` 的返回字典（`:1304-1341`）新增两个键：
  ```python
  "model": _string(raw.get("model")).strip(),
  "context_window": _coerce_clamped_int(raw.get("context_window"), 0, *AGENT_LOOP_CONTEXT_WINDOW_RANGE),
  ```
  **`0` 表示未配置**——沿用 `workdir` 的"空值 = 未设置"约定，避免为可选整数引入 `None`。

### 2.2 后端：model 流到 backend 实例
- `kagweb/services/agent_loop/__init__.py` `build_agent_loop_backend`：读 `resolved.get("model")`，传给三个分支的构造函数。
- `cli_backend.py` `CliAgentLoopBackend.__init__` 加 `model: str = ""`；`acp_backend.py` 同理（ACP 无 argv 替换，仅保存，供未来使用/日志）。
- `http_backend.py`：`HttpAgentLoopBackend.__init__` 与 `RunsAgentLoopBackend.__init__` 加 `model`；两个 `run()` 的 payload 在 **model 非空时**加 `"model"` 键。**空 model 不发该键**，保持与现状完全一致（不改变未配置部署的行为）。
- CLI `build_argv`：在现有 `{prompt}` 替换旁增加 `{model}` 替换，规则：
  - **model 非空** → `{model}` 替换为实际值（`--model {model}` 与 `--model={model}` 两种写法都对）；
  - **model 为空** → **整条含 `{model}` 的 argv 元素丢弃**（`--model={model}` 形式下这恰好精确；`--model {model}` 分离形式会留下裸 `--model`，故前端 helper 文本推荐同条写法）。
  - 保留一个**未配置 model 但用了 `{model}`** 的 debug 日志，避免静默。

### 2.3 后端：context_window 接进历史预算
这是本批最需要设计的一步，因为存在**时序约束**（已实测）：`executor.py:361` 建 context 时，`capability.py:125` 还没解析 profile。

- `kagweb/services/session/turns/request_preparer.py`：在已有的一次 `get_agent_loop_settings()` 读取处（P0 引入）**顺带提取** primary profile 的 `context_window`，非零时附加到 payload：
  ```python
  payload = {**payload, "agent_loop_context_window": <int>}
  ```
  - **放在 `TurnRequest.model_validate()` 之后**，因此不受 `extra="forbid"` 影响，也不污染公开协议。
  - **管理员与非管理员都要注入**（管理员同样需要正确的历史预算），因此读取移到分支之外——这与 P2-1「一次读取服务多处」的目标一致。
  - 该键**不会被持久化**：`_request_snapshot_metadata` 只挑固定键（已核实）。
- `kagweb/services/session/context_builder.py`：
  - `build()` 新增关键字参数 `context_window_override: int | None = None`。
  - `_effective_context_window(llm_config, override)` 优先返回 override（仍过 `min(..., MAX_EFFECTIVE_CONTEXT_WINDOW)`）。
  - 现有 4 处调用点（`:442`、`:443`、`:xxx` 预算计算）相应传递。
- `kagweb/services/session/turns/executor.py`：`builder.build(...)` 传入 `context_window_override=payload.get("agent_loop_context_window")`（缺失/0 → `None`，走原回落链）。

**效果**：agent-loop 部署下历史预算从 16K×0.35 ≈ 5,734 token 提升到后端真实窗口的 35%（如配 200000 → 70,000，受 `MAX_HISTORY_PLAN_TOKENS=131072` 上限约束）。

### 2.4 后端：API 与 bounds

## 风险与边界

| 风险 | 说明 |
|---|---|
| **`{model}` 未配置时的丢弃规则** | `--model {model}` 分离写法会留下裸 `--model`。这是**刻意的可预测规则**，前端 helper 会推荐 `--model={model}`。需你留意 ②：若你更希望"未配置时原样保留占位符"（让 CLI 自己报错），告诉我。 |
| **`context_window` 走内部 payload 键** | 不污染 `TurnRequest` 公开 schema（在 validate 之后附加），也不被持久化。代价是这个键名不在协议里，属内部约定——会在代码注释中写明。 |
| **管理员路径新增一次 settings 读** | 原本仅非管理员读。现两者都读，用于取 context_window。与 `ChatCapability.run` 的读取合计每回合 2 次；P2-1 已确认稳态下不写盘、仅多一次小文件读。 |
| **未配置时不改变行为** | model 为空不发 HTTP 字段、context_window 为 0 不注入 → 现有部署行为完全不变。 |
