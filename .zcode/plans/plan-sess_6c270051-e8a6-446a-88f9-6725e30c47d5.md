## 批次 0 — Intellect 对接修复（Rust-only，最高优先）

**判据**：不改则 Intellect 对接必然失败——预设指向不存在的端点，且 Rust 下文本/推理/工具/审批**四项全部静默丢弃**。

### 0a. 预设补齐
`kagweb/services/agent_loop/builtin.py:92-96`：
- `intellect-team` 补 `turn_path="/v1/runs"`、`protocol="runs"`（对齐 `intellect-runs:105-106` 的既有写法）。
- `description` 注明 **requires Rust api_server**（Rust-only 后连 Python 版会静默无输出）。

### 0b. 翻译器重写（核心）
`kagweb/services/agent_loop/http_backend.py:460-535`，判据从读 `event` 改为 **`type` 优先、`event` 兜底**——沿用仓库既有先例 `translate_generic`（`cli_backend.py:444` 已在用 `type or kind or event`），不发明新风格。

按权威 Rust 契约（文档 §C 实测表）分派：

| `type` | 产出 | 字段 |
|---|---|---|
| `assistant.delta` | 缓冲进 `content` | `text` |
| `reasoning.delta` | `thinking` | `text` |
| `thinking.progress` | 忽略（心跳，无文本） | — |
| `interim_assistant` | `content` | `content` |
| `assistant.completed` | `content` | `response` |
| `tool.started` | `tool_call` | `name`、`arguments` |
| `tool.completed` | `tool_result` | `name`、`result`、`duration_s` |
| `clarify` | `clarify_request` | `clarify_id`、`question`、`choices` |
| `approval.request` | `approval_request` | `tool_name`、`arguments`、`choices` |
| `error` / `run.failed` / `run.cancelled` | `error` | `message`/`error` |
| `run.completed` | 结算 + `usage` | `output`、`usage` |

保留 `tool.progress`/`run.*` 等仍由 `event` 表达的命名通道；`tool.failed` 作为 legacy 别名保留。缓冲刷新点不变（工具边界 + `run.completed`），`approval.request` 仍不刷新。

### 0c. 可观测性
同文件 `:535` 的静默 `return []` 改为 `logger.debug`（沿用 `_iter_ndjson:173` 的写法）。**这是本批最有价值的一行**：R18/R19 类故障之所以长期不可见，正因这里不报。

### 0d. `respond_clarify` 实现
同文件 `:539-553` 旁新增：`POST {url}/v1/chat/completions/{session_id}/clarify`，body `{clarify_id, answer}`。
- 注意端点**不在 `turn_path` 下**（是 `/v1/chat/completions/...`，非 `/v1/runs/...`）——需新增独立路径构造。
- 需捕获并保存 `session_id`（当前 `run()` 只存 `_run_id`，`:304`）。
- ACP 族的 `respond_clarify` 保持 `NotImplementedError`（`acp_backend.py:676`），但在计划中标注为已知不对齐项。

### 0e. capability 层一等 clarify 处理
`kagweb/capabilities/chat/capability.py`：
- `:307` 的控制门禁目前只认 `approval_request`，扩展为 `{"approval_request", "clarify_request"}`。
- 新增 `_handle_clarify_request`，**镜像 `_handle_approval_request`（:334-418）**：复用 `ask_user` 卡片通路（`tool_call` + `tool_result` 的 `tool_metadata.ask_user`）、复用 `wait_for_user_reply` 停等、复用 `ask_user_resolved` 解析标记。
- 复用/泛化 `_approval_question`（:902-922）：新增 `_clarify_question` 产出同一卡片形状（`id`/`header`/`prompt`/`options`/`multi_select`），选项来自 Rust 的 `choices`。
- 新增 i18n 词条到 `kagweb/services/i18n.py`（`agent_loop.clarify_*`，en/zh 双语，与 `approval_*` 同格式）。

**设计说明**：`clarify` 与 `approval` 的差别只在"选项来源"与"回传端点"，卡片渲染与答复读取完全同构，所以是镜像而非新机制。

### 0f. 测试
- `tests/services/agent_loop/test_runs_backend.py:15-31` 的 `SSE_BODY` **替换为权威 Rust 线上格式**（当前用的是 `delta`/`event:tool.started`，与错误实现同源，所以一直在验证 bug）。新增 4 条独立断言：文本、推理、工具、审批各一。
- 补充 clarify 分支测试 + `respond_clarify` 端点/body 断言（`_mock_backend` 加 `/clarify` 路由）。
- `tests/capabilities/test_chat_capability.py` 加一条 clarify 卡片测试，镜像既有 `test_approval_parks_and_forwards_label_decision`。
- `tests/api/test_agent_loop_settings_router.py:74` 的预设断言由子集 `<=` 收紧为包含 `intellect-team` 的路径/协议校验。

**验证**：`pytest tests/services/agent_loop tests/capabilities -q`

## 批次 2 — 解除多用户阻断（P0）

**问题**：纯 agent-loop 部署下，非管理员每一轮都被拒（`"No LLM model is assigned"`），因为门禁把"有 LLM 授权"等同于"允许聊天"，且在 agent backend 选择**之前**执行。

### 2a. 能力声明所需资源
`kagweb/core/capability_protocol.py:29-39` `CapabilityManifest` 增加 `required_service: str = "llm"`。

### 2b. 门禁解耦
`kagweb/services/session/turns/request_preparer.py:105-134`：
- 不再硬编码 `has_capability_access("llm")`，改为按 **有效所需资源** 判定。
- **chat 的特殊规则**：当 agent-loop 后端已配置时，chat 需要 `agent_loop` 而非 `llm`（manifest 是类级静态属性，无法按部署条件变化，所以这条规则放在 preparer 里，用一个 `_effective_required_service()` helper 表达，并注释说明理由）。
- 错误文案随之参数化。

### 2c. 授权维度
`kagweb/multi_user/grants.py`：
- `empty_grant()`（:23-52）的 `models` 增加 `agent_loop` 维度。
- `normalize_grant`/`validate_grant`（:104-132, :185-253）放行该维度。

### 2d. 访问判定
`kagweb/multi_user/model_access.py`：
- `redacted_model_access`（:71-116）为 `agent_loop` 产出一条**合成条目**（`{"available": <grant 决定>}`），使 `has_capability_access`（:141-154）无需改签名即可工作。
- **默认放行**：agent backend 已配置时，未显式拒绝的用户默认可聊——这符合产品意图（多用户部署应开箱可用），且不削弱 LLM 授权（LLM 仍是旁路调用的门）。

**这是本批唯一的语义决策点**，我会在实现时把 `agent_loop` 的默认值与拒绝语义写清并加测试。

### 2e. 测试（**当前完全缺失**）
已核实：仓库内**没有任何测试**钉住门禁行为，错误串 `"No LLM model is assigned"` 在测试中零出现，`request_preparer` 也无测试文件。需新增：
- 非管理员 + 已配置 agent backend → 轮次**被允许**（防回归）。
- 非管理员 + 无任何后端 + 无 LLM 授权 → 仍被拒。
- 管理员路径不变。
- `has_capability_access("agent_loop")` 的 admin/有授权/无授权三态。
